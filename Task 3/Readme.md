# T3. Архитектурное решение по трейсингу

## Список сервисов, которые должны попадать под трейсинг

1. **MES API**  
2. **Shop API**  
3. **CRM API**

## Мотивация

Трейсинг позволяет быстро находить проблемные места в системе, что способствует оперативному решению проблем. Кроме того, он даёт понимание того, в каких местах запросы обрабатываются с задержками.

## Предлагаемое решение

1. **Доработать приложения (MES API, Shop API, CRM API)** и добавить в них библиотеку телеметрии для маркирования запросов.  
2. **Развернуть сервер Jaeger** для сбора и визуализации запросов.

## Компромиссы

1. **Отсутствие пользы при отсутствии взаимодействия сервисов:** если сервисы не связаны между собой (3 отдельных UI и 3 отдельных сервиса), то цепочек вызовов практически нет, и можно обойтись мониторингом по кодам ответа (например, HTTP 500). В этом случае трейсинг даст мало преимуществ — поиск сбоев и так относительно прост.  
2. **Монолитные приложения:** в классическом монолите нет необходимости во внедрении распределённого трейсинга, так как вся логика сосредоточена в одном месте.  
3. **Коробочные решения:** если часть сервисов реализована в «коробочном» формате и недоступна для доработок, полноценную трассировку подключить будет невозможно.  
4. **Сложность при большом количестве сервисов:** доработка множества сервисов может быть трудозатратной, поэтому имеет смысл начинать с критичных цепочек взаимодействия, где видна наибольшая выгода от трейсинга.

## Безопасность

- Серверы с Jaeger и телеметрией должны быть расположены во внутреннем сегменте кластера.  
- Доступ во внутреннюю сеть рекомендуется организовать через VPN.  
- Доступ к UI Jaeger следует ограничить с помощью сертификата, логина и пароля, чтобы исключить несанкционированное проникновение.
