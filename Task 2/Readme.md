# T2. Выбор и настройка мониторинга в системе

## Мотивация

- **Контроль нагрузки на систему (сервисы):** позволяет определить места, где достигается критическая нагрузка, и заранее провести работы по повышению производительности.  
- **Определение проблемных мест (сбоев, ошибок):** повышает надёжность системы и даёт возможность вовремя исправить баги.  
- **Аналитика данных:** помогает понять бизнес-составляющую — например, какой функционал наиболее востребован.  
- **Улучшение клиентского опыта:** за счёт оптимизации производительности, быстрого обнаружения проблем и своевременных исправлений.

## Выбор подхода к мониторингу

Для сервисов кластера будем использовать подход «Четыре золотых сигнала», так как у нас много API, и данный метод наиболее эффективно выявляет аномалии в микросервисных приложениях.

## Отслеживание метрик

1. **Number of requests (RPS) for internet shop API** – определение нагрузки на API.  
2. **Number of requests (RPS) for CRM API** – определение нагрузки на API.  
3. **Number of requests (RPS) for MES API** – определение нагрузки на API.  
4. **Number of requests (RPS) per user for internet shop API** – определение нагрузки на API.  
5. **Number of requests (RPS) per user for CRM API** – определение нагрузки на API.  
6. **Number of requests (RPS) per user for MES API** – определение нагрузки на API.  
7. **CPU % for shop API** – показатель загрузки сервиса.  
8. **CPU % for CRM API** – показатель загрузки сервиса.  
9. **CPU % for MES API** – показатель загрузки сервиса.  
10. **Memory Utilization for shop API** – контроль потребления памяти, оценка утилизации и нагрузки.  
11. **Memory Utilization for CRM API** – контроль потребления памяти, оценка утилизации и нагрузки.  
12. **Memory Utilization for MES API** – контроль потребления памяти, оценка утилизации и нагрузки.  
13. **Memory Utilization for shop DB instance** – контроль потребления памяти, оценка утилизации и нагрузки.  
14. **Memory Utilization for MES DB instance** – контроль потребления памяти, оценка утилизации и нагрузки.  
15. **Number of connections for shop DB instance** – контроль подключений к БД для отслеживания лимита коннектов.  
16. **Number of connections for MES DB instance** – контроль подключений к БД для отслеживания лимита коннектов.  
17. **Response time (latency) for shop API** – контроль скорости ответов, оценка влияния на клиента и производительности сервиса.  
18. **Response time (latency) for CRM API** – контроль скорости ответов, оценка влияния на клиента и производительности сервиса.  
19. **Response time (latency) for MES API** – контроль скорости ответов, оценка влияния на клиента и производительности сервиса.  
20. **Size of shop DB instance** – контроль пределов по объёму хранимых данных.  
21. **Size of MES DB instance** – контроль пределов по объёму хранимых данных.  
22. **Number of HTTP 500 for shop API, CRM API, MES API** – контроль количества ошибок для оценки работоспособности системы и поиска сбоев.

## План действий

1. **Организовать сбор данных при помощи Prometheus**:  
   1. Поднять базу данных Time-Series.  
   2. Настроить Retrieval (сбор метрик).  
   3. Подключить HTTP-сервер.  
   4. Установить агенты-экспортеры.  
2. **Поднять сервер Grafana**.  
3. **Настроить дашборды** для визуализации метрик.  
4. **Сформировать алерты** (уведомления) при достижении критических значений.

## Показатели насыщенности

1. **Приближение к пороговым значениям RPS** – добавить экземпляры (инстансы) сервисов.  
2. **Превышение лимитов по CPU для БД** – доработать запросы к БД (завести тикеты на разработку), масштабировать кластер, увеличить количество шард, продумать кэширование.  
3. **Задержка с ответами на запрос** – масштабировать сервисы (увеличить количество экземпляров), завести тикет на разработку, продумать кэширование.
