# T5. Архитектурное решение по кешированию

## Решение

Рекомендуется применить кэширование для списка заказов, так как это наиболее частый запрос к системе.

## Мотивация

1. **Снижение нагрузки на БД:** благодаря кэшированию при получении списка заказов уменьшается количество запросов к базе данных.  
2. **Улучшение клиентского опыта:** пользователи получат информацию о списке заказов и их статусах быстрее, поскольку данные будут запрашиваться из кэша.

## Предлагаемое решение

1. **Выбрать подход *Refresh-ahead*:**  
   - Статус заказа может изменяться и без запроса пользователя (например, в рамках внутренней логики сервиса), поэтому важно периодически обновлять кэш данными из базы без ожидания запроса.  

2. **Альтернативные варианты и их недостатки:**  
   - **Cache-aside**: не совсем подходит, поскольку статус заказа может меняться «в фоне», а не только по инициативе пользователя. Пришлось бы настраивать слишком короткий TTL, что снизило бы эффективность кэширования.  
   - **Write-through**: при возникновении изменений в заказах, не идущих напрямую через пользовательский запрос (например, при взаимодействии нескольких сервисов), пришлось бы «принудительно» обновлять кэш. По сути это сводится к тому же *Refresh-ahead*, но с дополнительными усложнениями.

## UML-схема процесса Refresh-ahead

```plantuml
@startuml
title Refresh-ahead caching process for Orders table (jewelry manufacturing orders)

actor User
participant Cache
database Database as OrderDB

User -> Cache: Request list of orders
Cache -> Cache: Check cache validity
alt Cache is valid
    Cache -> User: Return data from cache
else Cache is about to expire or expired
    Cache -> Database: Fetch updated orders
    Database -> Cache: Return updated orders
    Cache -> Cache: Update cache
    Cache -> User: Return fresh data
end
@enduml
